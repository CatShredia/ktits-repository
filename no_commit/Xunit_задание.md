**3. Теоретическая часть**

**3.1. Понятие тестирования программного обеспечения**

Тестирование программного обеспечения — это процесс проверки соответствия разработанного приложения установленным требованиям, а также выявления ошибок и дефектов в его работе.

В процессе разработки приложения недостаточно проверить только то, что оно запускается и отображает необходимые окна. Необходимо убедиться, что отдельные программные компоненты выполняют свои функции правильно.

Например, если разрабатывается информационная система учёта товаров, необходимо проверить:

- корректность добавления нового товара;

- правильность расчёта стоимости;

- невозможность сохранения товара с отрицательной ценой;

- корректность поиска товара;

- правильность удаления записи из базы данных.

Для проверки отдельных компонентов используются тестовые модули.

**3.2. Модульное тестирование (Unit Testing)**

Модульное тестирование — это проверка отдельных небольших частей программы независимо от остальных компонентов системы.

В качестве объекта тестирования могут выступать:

- отдельный метод класса;

- отдельный класс;

- метод расчёта;

- метод проверки данных;

- компонент бизнес-логики;

- ViewModel приложения.

Например, в приложении имеется метод расчёта итоговой стоимости заказа:

public decimal CalculateTotal(

decimal price,

int quantity)

{

return price \* quantity;

}

Для проверки данного метода можно создать тест, который передаёт ему определённые значения и сравнивает полученный результат с ожидаемым.

Пример тестового метода:

\[Fact\]

public void CalculateTotal_ReturnsCorrectValue()

{

// Arrange

var price = 100m;

var quantity = 3;

// Act

var result = price \* quantity;

// Assert

Assert.Equal(300m, result);

}

В данном примере проверяется, что при цене 100 рублей и количестве 3 итоговая стоимость составляет 300 рублей.

**3.3. Структура тестового метода**

При разработке тестов рекомендуется использовать принцип AAA:

**Arrange — подготовка.**

На данном этапе создаются необходимые объекты, задаются исходные данные и подготавливаются условия тестирования.

**Act — выполнение.**

На данном этапе вызывается тестируемый метод или выполняется действие, которое необходимо проверить.

**Assert — проверка.**

На данном этапе полученный результат сравнивается с ожидаемым.

Пример:

\[Fact\]

public void CalculateDiscount_ReturnsCorrectValue()

{

// Arrange

decimal price = 1000m;

decimal discount = 10m;

// Act

decimal result = price -

(price \* discount / 100);

// Assert

Assert.Equal(900m, result);

}

Тест проверяет правильность расчёта стоимости товара со скидкой 10%.

**3.4. Инструменты модульного тестирования в C#**

Для разработки тестовых модулей в проектах на C# можно использовать следующие инструменты:

| **Инструмент** | **Назначение**                                    |
|----------------|---------------------------------------------------|
| xUnit          | Создание и выполнение тестов                      |
| NUnit          | Альтернативный инструмент модульного тестирования |
| MSTest         | Средство тестирования от Microsoft                |
| Moq            | Создание подменных объектов (моков)               |
| NSubstitute    | Создание подменных объектов                       |
| Coverlet       | Анализ покрытия кода тестами                      |

В рамках данной практической работы используется **xUnit**.

Основные атрибуты xUnit:

- \[Fact\] — обозначает обычный тестовый метод без параметров.

- \[Theory\] — обозначает тестовый метод, который может выполняться с различными наборами входных данных.

- \[InlineData\] — задаёт наборы параметров для тестового метода.

Пример использования \[Theory\]:

\[Theory\]

\[InlineData(100, 2, 200)\]

\[InlineData(50, 3, 150)\]

\[InlineData(25, 4, 100)\]

public void CalculateTotal_ReturnsCorrectValue(

decimal price,

int quantity,

decimal expected)

{

// Act

decimal result = price \* quantity;

// Assert

Assert.Equal(expected, result);

}

В результате один тестовый метод проверяется с тремя различными наборами входных данных.

**3.5. Организация тестирования проекта на Avalonia UI**

Avalonia UI — кроссплатформенный фреймворк для разработки пользовательских интерфейсов на C#.

В проектах на Avalonia часто применяется архитектурный подход MVVM (Model-View-ViewModel).

В рамках данной архитектуры приложение разделяется на несколько основных компонентов:

- **Model** — модели данных и предметной области.

- **View** — визуальные элементы интерфейса.

- **ViewModel** — логика взаимодействия интерфейса с данными и пользователем.

При разработке тестовых модулей рекомендуется в первую очередь проверять бизнес-логику, сервисы и ViewModel.

Например, если приложение содержит форму добавления товара, тестировать необходимо:

- проверку правильности введённой цены;

- проверку обязательных полей;

- корректность формирования объекта товара;

- правильность выполнения команды сохранения;

- обработку ошибок при сохранении.

Проверять непосредственно отображение кнопок и других элементов интерфейса с помощью обычных Unit-тестов не требуется. Для этого применяются отдельные подходы к UI-тестированию.

**3.6. Тестирование взаимодействия с PostgreSQL**

Если приложение использует PostgreSQL, необходимо проверять не только бизнес-логику, но и корректность работы компонентов, взаимодействующих с базой данных.

Например, приложение может содержать класс ProductRepository, отвечающий за работу с таблицей товаров.

В нём могут находиться методы:

- GetAll() — получение списка товаров;

- GetById(int id) — получение товара по идентификатору;

- Add(Product product) — добавление товара;

- Update(Product product) — изменение товара;

- Delete(int id) — удаление товара.

Для проверки подобных методов можно использовать интеграционные тесты.

**Важно различать два вида тестирования:**

1.  Модульное тестирование проверяет отдельный компонент независимо от реальной базы данных. Для этого можно использовать подменные объекты (Mock).

2.  Интеграционное тестирование проверяет взаимодействие нескольких компонентов, например репозитория с настоящей базой данных PostgreSQL.

Для интеграционных тестов рекомендуется использовать отдельную тестовую базу данных, чтобы не изменять реальные пользовательские данные.

При тестировании необходимо предусмотреть:

- проверку успешного добавления записи;

- проверку получения записи по идентификатору;

- проверку изменения данных;

- проверку удаления записи;

- проверку обработки ситуации, когда запись отсутствует.

**3.7. Создание отдельного тестового проекта**

Тестовые модули рекомендуется размещать в отдельном проекте, который связан с основным проектом приложения.

Например, структура решения может выглядеть следующим образом:

MyApplication

│

├── MyApplication

│ ├── Models

│ ├── Views

│ ├── ViewModels

│ ├── Services

│ ├── Repositories

│ └── App.axaml

│

├── MyApplication.Tests

│ ├── Services

│ │ └── ProductServiceTests.cs

│ ├── ViewModels

│ │ └── ProductViewModelTests.cs

│ └── Repositories

│ └── ProductRepositoryTests.cs

│

└── MyApplication.sln

Для создания тестового проекта можно использовать командную строку:

dotnet new xunit -n MyApplication.Tests

Для подключения тестируемого проекта:

dotnet add MyApplication.Tests reference MyApplication

Для установки необходимых пакетов:

dotnet add MyApplication.Tests package xunit

dotnet add MyApplication.Tests package xunit.runner.visualstudio

dotnet add MyApplication.Tests package Microsoft.NET.Test.Sdk

Если для работы с PostgreSQL используется библиотека Npgsql, интеграционные тесты должны использовать соответствующий драйвер и тестовую базу данных.

Для выполнения тестов применяется команда:

dotnet test

После выполнения команды разработчик получает информацию о количестве пройденных и не пройденных тестов.

**4. Практическая работа**

**Тема: Разработка тестовых модулей проекта для тестирования отдельных модулей**

**Задание**

Необходимо разработать тестовые модули для проверки отдельных компонентов информационной системы учёта товаров.

Для выполнения задания необходимо создать отдельный проект тестирования на основе xUnit и реализовать набор тестов для проверки бизнес-логики приложения и взаимодействия с PostgreSQL.

**4.1. Постановка задачи**

Разрабатывается информационная система учёта товаров.

Система должна обеспечивать:

- хранение информации о товарах;

- добавление новых товаров;

- изменение информации о товарах;

- удаление товаров;

- получение списка товаров;

- расчёт общей стоимости товаров;

- проверку корректности вводимых данных.

Для каждого товара предусмотрены следующие характеристики:

| **Поле** | **Тип данных** | **Описание**             |
|----------|----------------|--------------------------|
| Id       | int            | Уникальный идентификатор |
| Name     | string         | Наименование товара      |
| Price    | decimal        | Цена товара              |
| Quantity | int            | Количество товара        |
| Category | string         | Категория товара         |

**4.2. Этап 1. Создание тестируемого модуля**

В основном проекте необходимо создать класс Product, содержащий перечисленные выше свойства.

Пример:

public class Product

{

public int Id { get; set; }

public string Name { get; set; } = string.Empty;

public decimal Price { get; set; }

public int Quantity { get; set; }

public string Category { get; set; } = string.Empty;

}

Далее необходимо создать класс ProductService, который будет содержать методы обработки данных о товарах.

Необходимо реализовать следующие методы:

**1. CalculateTotalPrice()**

Принимает цену товара и количество, возвращает общую стоимость.

**2. CalculateDiscount()**

Принимает стоимость товара и процент скидки, возвращает стоимость с учётом скидки.

**3. ValidateProduct()**

Проверяет корректность данных товара.

Условия проверки:

- наименование товара не должно быть пустым;

- цена должна быть больше нуля;

- количество не может быть отрицательным;

- категория товара не должна быть пустой.

Методы должны возвращать результат вычисления или проверки. Для некорректных входных данных необходимо предусмотреть понятную обработку ошибок.

**4.3. Этап 2. Создание тестового проекта**

Необходимо создать отдельный проект с названием ProductManagement.Tests.

Требуется:

1.  Создать проект на основе шаблона xUnit.

2.  Добавить ссылку на основной проект приложения.

3.  Проверить наличие необходимых библиотек для тестирования.

4.  Создать папку Services.

5.  Создать класс ProductServiceTests.

**4.4. Этап 3. Разработка тестовых методов**

Необходимо разработать тестовые методы для проверки каждого метода класса ProductService.

**Задание 1. Тестирование расчёта стоимости товара**

Разработать тесты для проверки метода CalculateTotalPrice().

Проверить следующие ситуации:

| **Цена** | **Количество** | **Ожидаемый результат** |
|----------|----------------|-------------------------|
| 100      | 2              | 200                     |
| 250      | 4              | 1000                    |
| 50       | 0              | 0                       |
| 125,5    | 2              | 251                     |

**Задание 2. Тестирование расчёта скидки**

Разработать тесты для метода CalculateDiscount().

Проверить следующие ситуации:

| **Стоимость** | **Скидка** | **Ожидаемый результат** |
|---------------|------------|-------------------------|
| 1000          | 10%        | 900                     |
| 500           | 20%        | 400                     |
| 100           | 0%         | 100                     |
| 2000          | 50%        | 1000                    |

Дополнительно проверить обработку некорректного процента скидки, например отрицательного значения или значения больше 100%.

**Задание 3. Тестирование проверки данных товара**

Разработать тесты для метода ValidateProduct().

Необходимо проверить:

1.  Товар с корректно заполненными полями проходит проверку.

2.  Товар с пустым наименованием не проходит проверку.

3.  Товар с нулевой ценой не проходит проверку.

4.  Товар с отрицательной ценой не проходит проверку.

5.  Товар с отрицательным количеством не проходит проверку.

6.  Товар с пустой категорией не проходит проверку.

Для данного задания рекомендуется использовать атрибуты \[Fact\] и \[Theory\].

**4.5. Этап 4. Тестирование взаимодействия с PostgreSQL**

В основном проекте необходимо создать таблицу Products в базе данных PostgreSQL.

Пример SQL-запроса:

CREATE TABLE Products

(

Id SERIAL PRIMARY KEY,

Name VARCHAR(150) NOT NULL,

Price NUMERIC(10, 2) NOT NULL,

Quantity INTEGER NOT NULL,

Category VARCHAR(100) NOT NULL

);

Необходимо реализовать класс ProductRepository, который обеспечивает выполнение операций с таблицей Products.

Предусмотреть методы:

- Add(Product product);

- GetById(int id);

- GetAll();

- Update(Product product);

- Delete(int id).

Далее необходимо разработать тестовые методы для проверки работы репозитория с PostgreSQL.

Проверить следующие сценарии:

| **№** | **Проверяемое действие**         | **Ожидаемый результат**     |
|-------|----------------------------------|-----------------------------|
| 1     | Добавление нового товара         | Запись появляется в таблице |
| 2     | Получение товара по ID           | Возвращается нужный товар   |
| 3     | Получение несуществующего товара | Возвращается null           |
| 4     | Изменение информации о товаре    | Данные обновляются          |
| 5     | Удаление товара                  | Запись удаляется            |
| 6     | Получение списка товаров         | Возвращается список записей |

Для выполнения тестирования необходимо использовать отдельную тестовую базу данных PostgreSQL.

**Примечание:** тесты репозитория являются интеграционными, поскольку проверяют работу приложения с реальной базой данных. После каждого теста необходимо очищать тестовые данные или использовать транзакции с откатом изменений.

**4.6. Этап 5. Анализ результатов тестирования**

После разработки всех тестовых методов необходимо выполнить тестовый проект.

Для этого используется команда:

dotnet test

Необходимо убедиться, что:

- все тесты успешно запускаются;

- корректные входные данные обрабатываются правильно;

- некорректные входные данные выявляются;

- операции с PostgreSQL выполняются корректно;

- отсутствуют необработанные ошибки.

Для проверки работы тестов рекомендуется намеренно внести ошибку в один из методов основного проекта и повторно выполнить тестирование.

Например, изменить формулу расчёта общей стоимости товара.

После этого необходимо проанализировать, какой тест обнаружил ошибку и какое сообщение было выведено.

Затем исправить ошибку и повторно выполнить тестирование.
